# reactorとproactor：非同期操作の完全な一生

まず、あなたが最もよく知っているコードから：

```cpp
char buf[1024];
int n = recv(sock, buf, sizeof(buf), 0);
```

`recv` が戻った時、結果はすでに手の中にあります：データが得られたか、相手が切ったか、エラーが起きたか。関数の戻りが終わりです。これが同期です。

同期の問題は、待ちが 2 つ揃って初めて顕在化します。TCP サーバを書いて、同じスレッドで `accept` で新しい接続を待ち、確立済みの socket でデータを待つ——どちらかが先にブロックすると、もう一方は誰にも相手にされません。「終わり」が 2 つ、実行パスは 1 本、どちらか一方は必ず先へ進めません。

最も直感的な出路はスレッドを増やすこと：接続ごとに 1 スレッド、各スレッドが自分の `recv` を独占し、互いに遮りません。書くのは確かに楽で、実際に使えます。代償は接続数が増えた時にやって来ます——スレッドごとにスタック一式、カーネルのスケジューリングは順番に切り替え、大多数のスレッドは 99% の時間ただぶら下がっているだけです。接続数が数千・数万に達すると、あなたのサーバより先にスレッド方式が崩壊します。

別の道は「待つ」ことを集中させる：呼び出し点ごとにブロックさせるのではなく、**1 つのスレッドが大量のdescriptorを監視し、準備ができたものから処理する**。待ちが各 `recv` に散らかる代わりに、1 つのシステムコールに集約されます。これがreactorです。

さらに第 3 の道：「読む」「書く」という動作自体も委ねます。発起時には「読めるようになったら呼んで」と一言言うだけ。データはカーネルがバッファに運び、フレームが手渡すのはもう結果です。これがproactorです。

3 者の違いは 1 文に圧縮できます：**同期は自分でやって結果を持って続行；reactorが受け取るのは「動けるようになった」；proactorが受け取るのは「もう終わった」**。この章以降のすべては、最後の一文をコードの中で展開するものです。

## 二つのモデル

**reactor**：カーネルは「どのdescriptorが準備完了か」にだけ答え、`read`/`write` は自分でやるしかありません。select、poll、epoll、kqueue——そして Windows の WSAPoll も——すべてこの一族です。手に入るのは**準備完了通知**です。

**proactor**：I/O 自体はカーネルが完了させ、発起時にバッファを渡すと、コールバックが受け取るのは転送されたバイト数そのものです。Windows の IOCP（I/O Completion Port）は教科書的な実装です。手に入るのは**完了通知**です。

asio は両方のモデルを持ち、プラットフォームで切り替えます：

- **Windows**：IOCP を使う、真のproactor。発起時に OVERLAPPED 構造体とバッファをまとめてカーネルに渡し、完了ポートのキューから出てくるのは済んだ仕事です；
- **POSIX**：epoll/kqueue/select は本質的にreactorで、asio はそれらでproactorを**模倣**します——準備完了への関心を登録し、poll が準備を報告し、フレームが自分でシステムコールを実行し、結果を「完了」として handler に包装して渡す。模倣の鍵は最後の 1 ステップ：ユーザーに見せるのは「結果が届いた」だけであって「動いてよい」ではありません。

sasio は Windows 上であえて IOCP を使わず、模倣ルートを選び、WSAPoll をreactorに使います。理由は実質的です：IOCP の完了ポート、OVERLAPPED、`GetQueuedCompletionStatus` はモデルを一式の Win32 機構に埋めてしまい、読む人はまず Windows を登らないと非同期が見えません。WSAPoll 版の一行一行は socket の意味論の上に留まり、asio の POSIX バックエンド（`epoll_reactor` / `select_reactor`）と構造が同型です——階層と責務は 1 対 1 で対応し、コード量だけが一桁違います。代償は、本書が真のproactorを 1 つ講義しないこと——第 14 章の読書マップに `win_iocp_io_context` の補講パスがあります。

どちらのモデルでも、asio があなたに見せる API は同一です：`async_read_some` は両プラットフォームで同じ挙動をします。この「API 不変、バックエンドは変わる」という事実は、逆説的に**エンジン契約**がプラットフォームから独立して存在できることを証明しています。以下の 3 文が全書の基盤です。

## エンジン契約（全書 3 つの不変量）

**契約一：発起関数は handler を決してインライン実行しない。**I/O の完了（read/write/connect/accept/resolve）はすべて `scheduler::post` でキューに配送されます；期限切れのタイマーは scheduler が run ループ内で直接呼びます（これも発起関数内ではありません）；`dispatch` は「現在のスレッドがすでにこの context を処理している」時にのみインラインで実行します——これが唯一の正当な例外で、条件は検証可能です。発起関数がするのは 1 つのこと：「準備ができたら何をするか」を登録すること。（第 10 章の `strand::dispatch` は同じ原則が直列化層での再演です：判断対象が「この context」から「この strand」に変わり、同様に呼び出しスレッドが `run()` 内であることを要求します——asio の `strand_service::do_dispatch` の `can_dispatch() && !locked_` と一字違わず対応します。）

**契約二：handler は永遠に `run()` の中で実行される。**発起関数が返ると、あなたのプログラムは元の道を続けます；結果は未来のいつか、`run()` を呼んだ誰かのスレッドによって引き渡されます。`run()` がなければ、handler は 1 つも実行されません——データがずっと前に届いていても。sasio のすべての配送経路はこれを守り、strand も例外ではありません（第 10 章）。初心者に最も多い落とし穴はここです：post した後に `run()` を忘れると、コードは静かに何もしません。

**契約三：通知の源は 3 つだけ。**handler キュー（`post` されて来たもの）、準備完了の descriptor（reactor が報告）、期限切れのタイマー（ヒープの先頭）。エンジンの一周ごとに 3 つの源をすべて見直し、用があるものから処理します。マルチスレッドの競合、起床、停止規則は、すべてこの 3 つの源を軸に展開します。

この 3 文を暗記してください。第 4 章の work カウント、第 5 章の起床、第 6 章のキャンセルは、みなこの 3 文の基盤の上に成り立っています。後でどの挙動に驚かされても、契約に戻って読み直せば、たいてい自分で導き出せます。

## ある `async_read_some` の一生

最もよく使われるチェーンを見ます。シングルスレッド、socket 接続済み、相手はいつでも送れる状態：

```text
 user code                socket                  reactor                scheduler
    | async_read_some(buf,h)  |                       |                       |
    |------------------------->| store buf/h, register |                       |
    |                         | read interest         |                       |
    |                         |---------------------->| start_read(fd)        |
    |   returns (nothing happened yet)                 |                       |
    |<------------------------|                        |                       |
    |                         |                        |  WSAPoll(all fds)     |
    |                         |                        |== peer data arrives ==|
    |                         |  do_read(): recv()     |                       |
    |                         |<----------------------| invokes the registered |
    |                         |  got n bytes           | callback              |
    |                         |-------- post(h(n,ec)) --------->               | enqueue
    |                         |                        |                       |
    |     h(ec, n) runs inside the run() loop           |                       |
    |<--------------------------------------------------------- ------------|
```

このチェーンには 3 回の受け渡しがあります——シングルスレッドのプログラムなので、3 つのスレッドではなく 3 つの時点です：

1. **発起**：`async_read_some` はバッファと handler を socket オブジェクトに保存し、このdescriptorの読み準備への関心を reactor に登録して、返ります。データには触れていません——この時点で相手はまだ何も送っていないかもしれません；
2. **準備完了**：`run()` ループは `WSAPoll` で眠っています。相手のデータが到着し、poll が戻ると、reactor はこのdescriptorに登録されたコールバックを見つけて呼びます——そのコールバックはあなたの handler ではなく、socket 自身の `do_read` です；
3. **配送**：`do_read` が本物の `recv` を実行し、バイト数を得て、あなたの handler を結果とともに scheduler のキューに `post` します。run ループの次の周で取り出して実行します。

第 2 ステップと第 3 ステップの分業に注目：**reactor は「起こす」だけを担当し、本物の I/O をするのは socket の `do_read` です**。これが「reactorでproactorを模倣する」橋——起こした後にシステムコールを補えば、ユーザーが受け取るのはやはり完了通知です。契約一はこのチェーンで 2 回検証されました：発起時に handler は実行されず、`do_read` の後も実行せず（post しただけ）——あなたの handler が現れるのは常に第 4 ステップです。

マルチスレッドの `run()` はこのチェーンに競合を持ち込みます：2 つのスレッドが両方 `WSAPoll` で眠っている——誰を起こし、準備完了が二重に配送されることはないか。それは第 5 章の主題で、本書で最も見応えのあるバグの鉱脈です。

## 精読：エンジンループの骨格

あのチェーンは最終的に同じループに合流します。`src/scheduler.cpp` の `run_one_impl`（83 行）はライブラリ全体で最も重要なコードです。まず骨格を見ます——ロックとカウントを剥がし、形だけ残します：

```cpp
for (;;)
{
  if (stopped())                        // someone called stop(): quit now
    return false;

  if (!queue_.empty())                  // source 1: the handler queue
    { pop one and invoke it; return true; }

  if (earliest timer expired)           // source 2: the timer heap
    { pop and invoke its handler; return true; }

  timeout = next timer expiry;          // source 3 decides how long we may sleep
  reactor_.run_for(timeout);            // sleep in WSAPoll until any source fires
}
```

3 行がそれぞれ契約の着地点です：`return true` の前の実行が契約二（すべては run ループ内）；源 1 と源 2 の分かれ道——キューの handler は「誰かが post したもの」、タイマーの handler は scheduler が直接呼ぶ——は契約一の「キューを経由しない」です；末尾の 2 行は契約三の第 3 の源で、唯一ブロックする場所です。

もう 1 つの細部に、独立した段落を与える価値があります：`run_for` が戻ると、制御フローはループの頂上に戻り、**キューをもう一度見る**。なぜか？`WSAPoll` で眠っている間に、どのスレッドでも新しい handler を `post` した可能性があるからです——戻って見なければ、漏れます。エンジン全体の形はこの一言に尽きます：**毎周、3 つの源をすべて再確認する**。第 5 章では、「他のスレッドが post した後も眠っているスレッドが起こされる」ために asio と sasio がそれぞれ何を支払ったかを講義します。今はこの形だけ覚えてください。

骨格にはまだ 3 つの細部が消されています——work カウントが「やることが残っている」をどう判定するか、`stopped()` の後に未実行の handler はどこへ行くか、ロックをどんな順序で取ればデッドロックしないか——すべて第 4 章の全文精読で埋めます。

## 対照表

| 問題 | asio（Windows バックエンド） | asio（POSIX バックエンド） | sasio |
| --- | --- | --- | --- |
| 待機機構 | IOCP 完了ポート | epoll / kqueue / select | WSAPoll |
| 誰が I/O をするか | カーネル（真のproactor） | 準備後にフレームが自分で | 準備後にフレームが自分で |
| ソース入口 | `detail/win_iocp_io_context.hpp` | `detail/epoll_reactor.hpp`、`detail/select_reactor.hpp` | `src/reactor.cpp` |
| タイマーの駆動 | 完了ポートの待ちタイムアウト | reactor が poll タイムアウトを計算 | scheduler が poll タイムアウトを計算 |
| 対応関係 | —— | sasio と同型 | —— |

一言で：**sasio は asio の POSIX ルートを選び、それを Windows の上で走らせました**。sasio の reactor を読むことは、asio の `epoll_reactor` のミニチュアを読むことです。読み終えたら POSIX バックエンドの asio ソースに行っても、モデルの頭の切り替えは要りません。真のproactor（IOCP バックエンド）との差異は第 14 章に回します。

## 練習

**実験**：echo サーバをビルドして実行します：

```bat
cmake --build build --target ex03_echo_server
build\ex03_echo_server.exe 5555
```

端末を 2 つ開き、それぞれ `telnet 127.0.0.1 5555` で接続し、交互に文字を打つと、両方にエコーが返ります。単一の `run()` スレッドが 2 つの接続を同時にさばいている——本章のシーケンス図で説明してください：2 つの socket が同じdescriptorテーブルに登録され、1 回の `WSAPoll` が両方の準備完了を報告し、準備ができたものから処理します。片方を接続したまま送らないようにしてみてください：もう片方のエコーは影響を受けません。前者のdescriptorは準備ができておらず、ループはその上でシステムコールを無駄にしないからです。

**バグハント**：`tests/asio/steady_timer.cpp` を開き、cancel のケースを見つけてください：まず `expires_after` + `async_wait`、次に `cancel()`。戻り値は 1（1 つキャンセル）ですが、handler は**それでも呼ばれます**——`operation_aborted` を携えて。まず 2 つのことを予測：handler はいつどのスレッドで呼ばれるか？`cancel()` の呼び出しスタックの中で同期的に呼ばれたら何が起きるか？実行して検証してください。「キャンセルは通知なしを意味しない」が第 6 章の核心契約で、その理由（再入の回避）はもう予測できたはずです。

---

モデルは立ちました：発起は登録だけ、完了は `run()` の中、通知は 3 つの源から。しかし「発起は登録だけ」には前提があります——登録する場所がなければなりません。socket の状態はどこに保存されるのか、reactor とtimer heapは誰が持つのか、`io_context` 自身がほとんどロジックを持たないのはなぜか？次章：service registry。
